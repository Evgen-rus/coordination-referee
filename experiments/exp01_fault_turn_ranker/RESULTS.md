# Experiment 01 — обучаемый per-turn ranker для `fault_turn`

**Дата:** 2026-09-27
**Вердикт:** ❌ **НЕ ПЕРСПЕКТИВЕН** — hit@2 упал с 0.4074 до 0.1964 (Δ = −0.2110).
Baseline-правила оставлены нетронутыми и победили с большим отрывом.

> **Важное замечание к постановке.** В предыдущем отчёте я утверждал, что
> изменение локализации «поднимает Macro F1, Robustness F1 и Success F1».
> Это было неверно. `fault_turn_hit_at_k` — **единственная** функция в
> `evaluation/metrics.py`, читающая `t_pred`, и её вес в композите равен
> 0.10. Поскольку `localize(run, label)` принимает класс на вход,
> замена локализатора **не может** изменить ни Macro F1, ни Robustness F1,
> ни Success F1. Максимум, что даёт идеальная локализация, — +0.10 к
> composite. Ниже это подтверждено числами: все три метрики остались
> **бит-в-бит** теми же (0.7573 / 0.7154 / 0.8569) при смене локализатора.

## 2. Протокол и отсутствие утечки

Разбиения — те же `StratifiedKFold(3, shuffle=True, random_state=0)`, что и в
`scripts/local_cv.py`.

Внутри каждой fold (`tr` = обучение, `va` = валидация):

1. **OOF-метка класса** для `va` — LightGBM-мультикласс, обученный на `tr`,
   с официальными 122 признаками. На тесте истинного класса нет, поэтому
   честная оценка обязана опираться на **предсказанный** класс.
2. **Ranker обучается только на `tr`**: строки — только из сбойных ранов с
   `fault_turn ≥ 0` внутри `tr`.
3. **Решение класса-условное**: для каждого из 6 сбойных классов обучается
   свой бинарный «это ли fault_turn?» LightGBM. Это гарантирует, что
   ошибочно классифицированный ран всё равно получает ход, правдоподобный
   для предсказанного класса.
4. **Аргумент = argmax** по ходам рана. Для `clean` всегда `−1`.
5. **Валидационные метки и валидационный `fault_turn` не читаются** ни при
   построении признаков, ни при обучении.

Признаки ходов (115 шт.) строятся только из полей рана. Ключевые группы:
нормированная позиция; тип сообщения; роль/структура отправителя и
получателя; наличие `intent`; число `refs`; повторы текста и длина серии;
счётчики `handoff` по данному `intent` «до текущего хода»; число агентов над
интентом; признаки взаимного ожидания; префиксные счётчики `shared_state`
(включая «мигания» и `override`); артефакты и граф коммуникаций «до текущего
хода»; rolling-окна ±2 и ±5; изменение goal-overlap относительно
предыдущих ходов. Плюс one-hot класса рана (6 значений на train по истинному
классу, на валидации — по предсказанному).

### Аудит утечек — PASS

```
1. AST check: does build_turn_matrix read the target or the label?
   fault_turn  as identifier=False as key/index=False -> clean
   label       as identifier=False as key/index=False -> clean
   success     as identifier=False as key/index=False -> clean
2. label/target injected into the run dict -> features identical?
   identical for all 60 runs: True
3. causality: corrupt turns after t, check turns <= t
   runs with UNEXPECTED differences           : 0
LEAKAGE AUDIT: PASS
```

Признаки инвариантны к corrupting будущих ходов, кроме явно перечисленных
оконных ±2/±5 и run-статистик, которые читают только содержимое протокола
(тип, интенты, повторы), но не метку и не цель.

| Метрика | Правила | Ranker | Δ |
|---|---|---|---|
| **fault_turn_hit@2** | **0.4074** | **0.1964** | **−0.2110** |
| Macro F1 | 0.7573 | 0.7573 | 0.0000 |
| Robustness F1 | 0.7154 | 0.7154 | 0.0000 |
| Success F1 | 0.8569 | 0.8569 | 0.0000 |
| **Composite** | **0.7267** | **0.7056** | **−0.0211** |

`Δcomposite = 0.10 × Δhit@2 = 0.10 × (−0.2110) = −0.0211` — сходится в точности.

## 4. Почему провал — это не шум

Диагностика (`diag1.py`) дала четыре независимых объяснения.

**(1) Смещение к началу рана.** Истинный `fault_turn` приходится на первые
10 % рана: `runaway_loop` 76 %, `goal_drift` 48 %, `deadlock` 46 %,
`dropped_handoff` 39 %. Раннер же выбирает argmax, а у классов с поздним
сбоем (`duplicated_work` медиана 0.585 длины, `conflict` 0.467) все
поздние повторы выглядят не хуже ранних.

**(2) Потеря ограничения «первое подходящее событие».** Диагностика показала,
что определяющее событие класса срабатывает на истинном `fault_turn`
**в 100 % случаев** (`is_assign` для `dropped_handoff`,
`is_second_assign_intent` для `duplicated_work`, `state_is_override` для
`conflict`). То есть цель идентифицируема — но pointwise-модель не
закодирована на «вернуть **первое** такое событие», а правила
`localize()` именно так и устроены. Отсюда коллапс
`conflict` 0.873 → 0.004: правило возвращает первую перезапись горячего
ключа и почти всегда попадает в цель, а раннер выбирает максимум среди
всех последующих перезаписей.

**(3) Потолок «никогда не доставлено».** `dropped_handoff` по онтологии —
это назначение, по которому артефакт **так и не появился**. Строго
причинная модель на ходе `t` видит только доставки до `t`: 37.7 %
назначений в этих ранах не имеют доставки вообще, и снабдить их признаком
«нет доставки» можно только заглянув вперёд. Правила `localize()` на это
смотрят свободно. Это не утечка, а принципиальный разрыв в информации,
который у причинного раннера закрыть нельзя.

**(4) Единственный выигрыш — `runaway_loop`** (0.265 → 0.447). Там истина
концентрируется в начале рана (76 % в первых 10 %), поэтому pointwise
модель с уклоном к ранним повторам угадывает. Это подтверждает диагноз:
раннер не «плохой», он оптимизирует не то, что нужно.

## 5. Что это значит для следующих шагов

* Порог успеха из задания (**+0.05**) не достигнут — с огромным минусом.
* По инструкции усложнять модель дальше **без отдельного обоснования
  нельзя**. Обоснование, которое стоит рассмотреть, — не «больше
  деревьев», а смена постановки:
  1. **Добавить некаузальные (forward) признаки**, разрешённые рамками
     задачи, — «назначение так и не было доставлено»,
     «второе назначение с артефактом», «после хода `t` артефактов не
     появилось». Это снимает потолок пункта 3, а forward-окна тут не
     утечка: на тесте весь раун известен, а разметки нет.
  2. **Закодировать ограничение «первое событие»** — например, обучать
     рангер не на абсолютном argmax, а на выборе первого
     квалифицирующего события, что по природе совпадает с онтологией.
  3. Только после этого имеет смысл подбирать гиперпараметры.
* Локализатор **не** трогать, пока не проверены пункты 1–2: правила дают
  0.407, и их нечем заменить, не получив прирост.
* Формат предсказаний не нарушен: для `clean` всегда `−1` (0 нарушений),
  ответы остаются целыми и в диапазоне рана.
